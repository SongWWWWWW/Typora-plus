# Typora Plus Architecture

## Principles

Typora Plus keeps the writing surface simple while keeping the system extensible:

- Markdown files are the future source of truth.
- UI consumes services and tokens instead of owning platform behavior.
- Core packages stay small; feature growth should move through contrib or extension-style boundaries.
- Configuration defaults are centralized.
- Theme values are centralized as CSS tokens.
- Heavy work such as indexing, export, and extension execution must not block editor input.

## Package Layers

```text
packages/base        lifecycle, events, URI, low-level utilities
packages/platform    service container, configuration, commands, text-file model
packages/markdown    Markdown outline, stats, document helpers
packages/theme       theme resolution and CSS design tokens
packages/editor      CodeMirror-backed Markdown editor
packages/workbench   application layout, commands, sidebar, statusbar
apps/desktop         renderer entry, Vite config, Electron shell
```

Dependency direction is upward only:

```text
base -> platform -> workbench -> app
markdown -> editor -> workbench -> app
theme -> workbench/app
```

The editor package does not know about files, windows, Electron, or sidebars. The workbench does not parse Markdown manually beyond calling the Markdown package. The desktop app only bootstraps services and shell entry points.

Architecture boundary tests scan package source imports, workspace package dependency declarations, and TypeScript project references against this dependency direction. A package cannot start depending on a higher layer without failing the normal test suite.

The desktop renderer build uses manual chunks for the largest runtime families. CodeMirror core, CodeMirror language support, React, generic vendor code, and the built-in Mermaid renderer dependency graph are separated so Mermaid can remain a lazy-loaded preview feature instead of increasing the startup bundle.

## Services

Current services:

- `IConfigurationService`: centralized and persisted appearance, editor, workspace, AI provider, and remote sync provider profile defaults
- `IContextKeyService`: structured context values and expression evaluation for conditional contributions
- `ICommandService`: command metadata registration, command handler registration, metadata change events, async execution, and command activation bridging
- `IExtensionService`: static extension manifest registration, theme contributions, activation events, and constrained runtime command/context-key/AI-provider/export-provider/Markdown renderer/remote-sync provider APIs
- `IExtensionHostService`: extension host registration, unambiguous host routing, and activation dispatch
- `IKeybindingService`: keybinding registration, keyboard event resolution, and async command dispatch
- `IMenuService`: menu/action contribution registration for Workbench surfaces such as titlebar and activitybar
- `ITextFileService`: active Markdown model, dirty state, conflict-aware save lifecycle
- `IWorkspaceService`: workspace identity
- `IFileService`: native workspace file tree, trusted recent workspace reopen, workspace change events, file open, save, save-as
- `IAttachmentService`: pasted image persistence through a native bridge
- `IRecentService`: persisted recent files and workspaces
- `IIndexService`: asynchronous workspace indexing, cross-file search, Markdown metadata collection, backlink/link graph queries, and tag queries through a replaceable index provider
- `IResourceService`: workspace-backed preview resource resolution through a native bridge
- `IExportService`: registered export providers, exported document generation, and native/browser save routing
- `IMarkdownRendererService`: registered Markdown renderer metadata, provider lifecycle, rendering delegation, and change events
- `IAiService`: registered AI providers and normalized text request delegation for future writing-assistant, workspace-grounded, OpenAI, Codex, or local-model integrations
- `IRemoteSyncService`: registered remote sync providers, workspace sync planning, execution-side classification, execution delegation, extension/runtime provider registration, and normalized conflict/reporting metadata for future Feishu Drive or other cloud integrations
- `IRemoteSyncWorkspaceResourceService`: provider-neutral read/write/delete access to bounded file content in the active trusted workspace for future remote sync adapters
- `IThemeService`: registered theme contributions, theme change events, and theme token validation

Remote sync native requests support UTF-8/base64 bodies and structured multipart text/file parts. The renderer passes multipart parts as data, not prebuilt `FormData`; Electron validates part counts, field names, file names, content types, decoded request size, secret bindings, and caller headers before constructing `FormData` in the main process. Multipart requests cannot also provide raw bodies, JSON secret fields, `bodyEncoding`, or caller-owned `Content-Type`, so future upload adapters do not own multipart boundary generation or secret injection policy.

Remote sync workspace resource access is a separate native bridge from ordinary Markdown file editing. Providers pass a workspace URI plus a workspace-relative path and base64 content through `IRemoteSyncWorkspaceResourceService`; Electron verifies the workspace is the active trusted root, rejects absolute paths, URI schemes, parent traversal, ignored-directory segments, symlink/realpath escapes, oversized resources, directories, invalid base64, and stale writes/deletes before reading, writing, or unlinking a file. Native reads return `sha256:` content hashes with the bounded base64 content, and the platform can compute the same hash with Web Crypto as a fallback when a non-native bridge omits it. This keeps future upload/download adapters from using unrestricted filesystem APIs while still allowing Markdown assets and raw mirrored files to move through a bounded service.

Markdown asset discovery for remote sync is parser-backed and provider-neutral. The Markdown package collects local image and link references from inline and reference-style Markdown tokens, resolves them relative to the source note, strips query/fragment suffixes, URL-decodes safe path text, deduplicates by workspace-relative path, and rejects schemes, absolute paths, fragment-only targets, invalid encodings, and root-escaping traversal. Workbench only runs this discovery when the native workspace resource bridge is available: it reads Markdown files through `IRemoteSyncWorkspaceResourceService`, verifies each discovered resource through the same bridge before adding it to the plan, skips missing assets, and keeps already-hashed resources out of duplicate content reads. This keeps Markdown syntax knowledge out of remote sync providers while giving future raw file mirrors the note assets they need.

Native workspace trust is owned by the Electron main process. The renderer may request a recent workspace by URI, but the main process only opens paths previously selected through the native directory picker and recorded in the main-process trust store.

Preview resources are also resolved by the platform layer. The renderer passes the active note URI and Markdown image source through `IResourceService`; the Electron main process rejects protocols, absolute paths, path traversal, unsupported extensions, and oversized images before returning a renderer-safe data URL. Workbench translates editor content updates, editor preferences, preview resource availability, pasted-image attachment handling, and Markdown renderer providers into `MarkdownEditor` adapter props through a focused editor adapter helper instead of constructing those boundaries inline in the shell.

Workbench navigation surfaces, including search, outline, files, backlinks, and tags, consume package/service contracts. Backlinks and tags are queried through `IIndexService`; Workbench opens indexed source notes and scrolls to indexed lines without resolving Markdown links or processing raw tag metadata itself. Search result formatting, local document matching, result keys, and backlink/tag display helpers live in a focused Workbench search model, so the shell component does not own query parsing or keyed result formatting. Search/backlink/tag query selection lives in a focused Workbench navigation query helper that chooses local document search when no workspace is open and index-backed queries when workspace data is available. Search results, backlinks, and tagged resources that target file lines share a focused line-navigation helper that chooses immediate local scrolling or resource opening, creates reusable target-open handlers for Sidebar surfaces, reuses ordinary file opening for URI targets, maps open failures through the action runner, clears stale save conflicts, adapts editor handles through a shell-provided source, and defers line scrolling through an injected timer until after the new editor model has mounted. Tag selection normalization, invalid-selection fallback, selected-tag synchronization, and active tag row state live in a focused Workbench tags model, keeping tag matching policy aligned with the index service without copying case-insensitive checks into JSX. Ordinary file-opening paths share a Workbench file-opening helper that clears stale save conflicts, delegates to `ITextFileService.openFile()`, and records the opened model through `IRecentService`. Workspace open, trusted recent workspace reopen, and workspace refresh share a Workbench workspace-opening helper that maps native file trees to `WorkspaceState`, records recent workspaces only for open/reopen flows, and opens the first workspace file through the same file-opening helper. File-tree row flattening, depth calculation, row identity, active-state checks, dirty indicators, and file-entry narrowing live in a Workbench file tree model. Recent resource section grouping, per-section limits, row keys, active-state checks, and file-entry mapping live in a Workbench recent resources model, keeping Files sidebar history behavior out of JSX. File, recent-workspace, and Quick Open selection follow-up lives in a focused resource-opening helper that reuses the same open paths and creates shell follow-up callbacks before asking the shell to clear conflicts, reveal the named Files side view, or close Quick Open; file-tree, recent-workspace, and Quick Open selections use Workbench-local handler factories before crossing the shared action boundary, so React surfaces do not duplicate operation-error or save-conflict mapping.

Successful workspace saves refresh the saved file's index record through `IIndexService.indexFile(file, value?)`. A focused saved-file indexing helper maps the saved model to the current workspace file entry, passes saved content, refreshes the workspace tree once when save-as creates a file that is not listed yet, and synchronizes refreshed workspace state through `IWorkspaceService`. Workbench save and save-as coordination lives in a focused file-saving helper that delegates to `ITextFileService`, records recent saved files through `IRecentService` when appropriate, and then reuses the saved-file indexing helper. Auto-save scheduling, dirty/file/conflict guards, configured delay handling, browser timer adaptation, and recent-tracking suppression live in a focused auto-save helper that reuses the same file-saving path. Save-conflict callback creation, dialog action handler creation, reload, and overwrite actions live in a focused conflict-resolution helper that reuses file opening, saving, indexing, and action-runner error mapping before asking the shell to clear dialog state. Markdown search, tag, and backlink extraction remain owned by the platform index provider.

`WorkspaceIndexService` owns scan orchestration and status updates. Indexed storage and query behavior sit behind `WorkspaceIndexProvider`; `InMemoryWorkspaceIndexProvider` owns query behavior, while `PersistedWorkspaceIndexProvider` adds a versioned, workspace-scoped snapshot cache through an injected storage boundary without changing Workbench consumers. Workspace snapshot keys are derived from the workspace root URI, so multiple workspaces do not overwrite each other's cached index. Desktop builds resolve the snapshot storage boundary through a narrow Electron preload bridge into main-process app data files; browser builds fall back to local storage. Batch hooks keep full workspace scans from writing a snapshot for every indexed file, and generation checks prevent canceled scans from writing stale documents after a newer scan has started. A future SQLite provider should implement the same storage/query contract. Search result limits are applied through the index service configuration boundary for workspace search and through the Workbench search model for local-document search, so Settings changes affect both query paths immediately and file-size changes trigger Workbench to reindex the current workspace through a focused workspace-indexing handler and action helper.

Keyboard shortcuts are resolved through `IKeybindingService` instead of hard-coded Workbench key checks. Workbench registers its default shortcuts as keybinding rules and dispatches resolved commands through `ICommandService`; command palette rows can read and search active labels from the same service through a focused command palette model, and command palette execution handler/callback factories use the same action boundary before closing the palette surface. A focused command surface helper captures the command metadata snapshot and supplies command-title and keybinding-label callbacks to titlebar, activitybar, Command Palette, and Settings surfaces. Workbench subscribes to command metadata changes through the centralized state subscription helper and refreshes that command surface snapshot from a revision state, so dynamic command contributions can update command-driven surfaces without polling. Workbench browser keydown target adaptation, listener lifecycle, default prevention, and resolved-command dispatch live in a focused keybinding dispatch helper, keeping browser input handling separate from the React shell. Workbench command dispatch and async UI actions share a focused action runner that clears stale operation errors, maps save conflicts into dialog state, preserves generic operation errors, and creates reusable command executors for shell surfaces without letting React components duplicate error handling. Built-in Workbench command ids live in a focused command id model consumed by registrations, default menus, default keybindings, command metadata, and sidebar command handlers. Built-in command titles and categories live in a focused command metadata model, while executable handler registration lives in a focused command registration helper that wires current configuration, workspace files, editor handles, and shell callbacks into `ICommandService`. `ICommandService` keeps command metadata separate from executable handlers: metadata feeds command palette and Settings surfaces, while execution only succeeds when a handler is registered. Metadata registrations are observable through a command-change event so future dynamic contributions, including provider-backed AI or sync commands, can refresh command surfaces without polling. Command execution is asynchronous. When a command has metadata but no handler, the command service calls its injected activation handler, then retries handler lookup before failing with a no-handler error. User keybinding overrides are persisted as validated configuration and applied as higher-priority keybinding rules, keeping the VS Code-like split between default contributions and user preferences. A shortcut label is only returned when that binding is currently effective for the command, so shadowed defaults do not mislead the UI.

Titlebar and activitybar actions are resolved through `IMenuService` instead of fixed button lists inside React components. Workbench default actions live in `workbenchContributions.ts` with stable menu ids, command ids, icon ids, order metadata, compact visibility, toggle context, and optional `when` expressions. `IContextKeyService` owns structured context values and expression evaluation, and `MenuService` filters contributed items when context changes. The platform also exposes a constrained `when` parser for manifest-style strings with keys, `!`, `==`, `!=`, `&&`, `||`, parentheses, and primitive values; it creates structured expressions rather than executing code. Workbench context key names, capability snapshots, capability-context application, state snapshots, provider availability snapshots, and state-context application live in a focused context model that applies active resource scheme, side view, editor modes, workspace availability, AI provider availability, remote sync provider availability, and native capability availability through `IContextKeyService`. Workbench menu ids, menu item reads, menu-change subscriptions, title fallback, menu context construction, and toggled active-state checks live in a focused menu model so titlebar/activitybar behavior is tested without React. Workbench menu icon ids, theme-aware icon resolution, and known-id checks live in a pure menu icon model, while the local React icon renderer is a thin Workbench UI layer; the shell renders filtered contributions without owning contribution icon policy. This mirrors VS Code-style contribution registration: commands, keybindings, menus, icons, and context keys are separate contribution points that can later be fed by extensions without rewriting the shell.

`IExtensionService` is the current manifest and runtime API boundary. It accepts extension manifests with command, menu, keybinding, theme, Markdown renderer, and activation-event contributions, validates required ids and primitive fields, parses menu `when` strings into structured context expressions, registers contributions through the existing command/menu/keybinding/theme/Markdown renderer services, and returns one disposable that unregisters the whole extension. Registration failures roll back partial contributions. Manifest commands register command metadata and derive `onCommand:<command>` activation events. Manifest themes register through `IThemeService`, which validates Typora Plus CSS token names, rejects unsafe token values, and publishes theme changes before exposing theme metadata. Manifest Markdown renderers register through `IMarkdownRendererService`, derive `onMarkdownRenderer:<id>` activation events, and remain metadata-only until activation supplies a runtime provider. The Workbench listens for theme changes, stores the selected theme id in configuration, and applies selected themes as a safe CSS-variable overlay through the theme package; removing a theme or choosing Default clears previously applied token overrides. A focused Workbench theme application helper owns selected-theme lookup, system color-scheme fallback, and token-overlay application, while a focused theme synchronization helper owns browser/document environment creation, `matchMedia` listener lifecycle, and document-root application. `activateByEvent()` indexes matching extensions, tracks inactive/activating/activated/failed states, creates an `ExtensionContext`, and delegates activation to `IExtensionHostService`. That context exposes a constrained command API for registering runtime command handlers, executing commands, and reading command metadata; a constrained context-key API for setting and reading extension-owned keys under the extension id namespace; a constrained AI API for registering provider-backed text providers through `IAiService`; a constrained export API for registering provider-backed export formats through `IExportService`; a constrained Markdown API for registering renderer providers through `IMarkdownRendererService`; a constrained remote sync API for registering workspace sync providers through `IRemoteSyncService`; and a subscription store owned by the extension record. Runtime command registrations, extension-owned context keys, extension AI providers, extension export providers, extension Markdown renderer providers, and extension remote sync providers are cleared when activation fails or when the extension is unregistered. `IExtensionHostService` registers extension hosts, rejects duplicate host ids, rejects missing hosts, and rejects ambiguous matches so activation routing stays explicit. Extension host protocol messages now define wire-safe handshake request/result payloads, activation request/result/error payloads, plus command, context-key, AI-provider, export-provider, Markdown-renderer, and remote-sync broker payloads that can cross an out-of-process boundary. Handshake messages carry the protocol version and bounded capability ids so future adapters can fail fast before activation when a peer is incompatible. Protocol command messages cover runtime command registration, command unregistration, command execution with bounded JSON arguments, and command list requests; context-key messages cover extension-owned key set/clear/get requests with primitive values only; AI messages cover provider registration, provider unregistration, text requests, text results, bounded request context, metadata, model names, token usage, and provider-scoped cancellation; export messages cover provider registration, provider unregistration, export document requests, exported document results, bounded asset metadata, image MIME types, relative asset paths, and base64 payloads; Markdown-renderer messages cover provider registration, provider unregistration, render requests, render results, bounded source text, bounded HTML, renderer metadata, and language normalization; remote-sync messages cover provider registration, provider unregistration, create-plan requests/results/cancellation, execute-plan requests/results/cancellation, bounded workspace resources, workspace-relative operation paths, operation summaries, dry-run intent, and metadata. `ExtensionHostRuntimeBroker` consumes the runtime API side of those messages for one activated extension context, maps them onto the constrained context APIs, registers and unregisters proxy command/AI/export/renderer/remote-sync providers, and calls an injected request function for future host-side command handlers and provider callbacks. `ExtensionHostProtocolSession` wraps a transport-shaped `send`/`onMessage` pair, owns request id generation, optional reusable handshake dispatch, pending request correlation, activation request dispatch, inbound runtime API routing through the broker, response identity checks, optional injected request timeouts, error reporting, and broker lifetime. When `requireHandshake` is enabled, activation waits for a compatible handshake result before sending activation. `ExtensionHostProtocolHost` implements the existing `ExtensionHost` interface, uses a caller-provided transport factory to create one protocol session per extension id, reuses that session across activations, passes request timeout and handshake policy into the session, and ties session disposal to both host disposal and the extension subscription lifecycle. `ExtensionHostProtocolRuntime` is the protocol peer for a future out-of-process runtime: it responds to protocol handshake requests, receives activation messages, creates a constrained proxy `ExtensionContext`, invokes an injected activation handler, sends runtime contribution register/unregister messages, handles main-side command/AI/export/renderer/remote-sync callback requests, forwards provider-scoped cancellation into runtime `AbortSignal`s, applies the same optional request timeout lifecycle for outbound runtime API calls, and converts callback failures into API error responses. `ExtensionHostProtocolRequestTimer` keeps timeout scheduling injectable so tests, workers, Electron IPC, or a future process host can control clock behavior without hard-coding timers into transport code. `ExtensionHostProtocolWireTransport` adapts the protocol transport contract to an injected string channel, serializes outbound messages, deserializes inbound messages, reports invalid inbound wire data, and can enforce an injected maximum wire-message length before future IPC adapters are connected. `ExtensionHostProtocolConfiguration` maps platform configuration into session, runtime, and wire transport options, treating zero values as disabled and preserving explicit adapter options. `createLinkedExtensionHostProtocolTransports()` provides a platform-only test transport pair that JSON round-trips every protocol message, enabling host/session/runtime end-to-end verification without pretending to be real IPC. The protocol host, session, broker, runtime facade, request timer, wire transport, configuration mapper, and linked test transport do not own IPC, load extension code, or expose internal services. These messages include request ids, extension ids, bounded strings, bounded JSON values where appropriate, and bounded error details, but intentionally exclude `ExtensionContext` functions and internal service instances. Workbench wires the command service activation handler to `activateByEvent("onCommand:<command>")`, so command palette, keybinding, and menu command execution can activate a matching extension before command execution is retried. Workbench also wires the Markdown renderer service activation handler to `activateByEvent("onMarkdownRenderer:<id>")`, so renderer execution can activate a matching extension before provider lookup is retried. Workbench default menus, shortcuts, the built-in Ink theme, and the built-in Mermaid and Status renderer metadata are supplied through a built-in extension manifest, while built-in Workbench command handlers are registered by the Workbench command registration helper. The in-process Workbench extension host only handles the built-in extension runtime and registers the Mermaid and Status providers through the same `ExtensionContext.markdown` API that future hosts will broker; a future out-of-process host can use the same context boundary without exposing internal services, DOM access, or unrestricted Node access.

User preferences are owned by `IConfigurationService`. The service reads and writes validated configuration through an injected storage boundary, so Workbench commands update preferences through the service without accessing storage directly. Editor behavior defaults, including auto-save timing and renderer preview cache size, live in configuration rather than Workbench constants. Markdown workflow defaults, including the Status badge vocabulary, also live in configuration with bounded validation so built-in renderers do not carry private alias tables. Extension-host protocol policy, including request timeout and wire-message length limits, lives in configuration so future adapters do not copy private constants. Appearance preferences include the base color scheme and an optional selected theme id; clearing the selected theme id removes the custom token overlay rather than leaving stale CSS variables. Numeric configuration bounds are platform-owned, persisted numeric values are clamped by the configuration layer before consumers read them, and defaults stay aligned with control steps so Settings does not display divergent slider and number values. Workspace preference changes are synchronized into the affected platform services, including index limits and attachment asset folders. A focused Workbench configuration sync helper applies those runtime preferences to attachment, index, and keybinding services at startup and after configuration changes, keeping React effects and service bootstrap from duplicating field mapping. A focused Workbench initial-state helper captures the startup snapshot for configuration, active model, workspace, recents, themes, and index status before a focused state subscription helper owns later service listener lifecycle for those same streams plus Markdown renderer revisions and native workspace-file updates; the React shell supplies only state setters and still does not reach into service internals. In Electron, the preload bridge routes configuration storage to a main-process file under the app data directory; browser builds fall back to browser storage.

The settings UI is a Workbench contribution, not a storage owner. `SettingsDialog` renders appearance, custom theme, editor, renderer preview cache, workspace, and keybinding controls, then sends partial updates through a focused configuration-update handler and action helper into `IConfigurationService` so storage failures use the same operation-error boundary as other Workbench actions. Settings section ids, entry ids, the default section id, section definitions, section anchors, section title lookup, searchable setting entries, search visibility state, entry labels, typed option metadata, registered-theme option formatting, selected-theme fallback, visible-section fallback, nearest-section selection, asset-folder normalization and commit resolution, keybinding command/shortcut-label search, modified filtering, and keybinding override list updates live in focused Workbench models so the dialog can grow without scattering UI constants. The dialog consumes entry labels and select/segmented-control options from the Settings model, keeping rendered controls aligned with search metadata, registered theme metadata, and platform configuration types; it still owns DOM measurement for scroll synchronization but delegates search visibility and section selection policy to the model. Numeric Settings controls reuse platform configuration constraints, including megabyte display conversion for workspace file-size limits, and route raw input parsing, clamping, and invalid-input handling through the Settings model so UI bounds, edit behavior, and stored-value validation stay aligned. When a recorded shortcut is already active for another command, Settings shows an inline conflict confirmation before writing the override. Batch keybinding reset clears persisted user overrides through the same configuration boundary instead of mutating keybinding service state directly.

Keyboard-driven list surfaces share small Workbench models. Command Palette and Quick Open keep local active-row state, but bounds normalization and Arrow/Home/End movement live in `listNavigationModel.ts`, so new palette-like surfaces can reuse the same behavior without copying key handling into JSX. Overlay input focus scheduling, browser timer cleanup, and missing-target tolerance live in a focused overlay-focus helper shared by Command Palette and Quick Open. Quick Open file filtering, ranking, and result limiting live in `workbenchQuickOpenModel.ts`; the maximum result count comes from platform workspace configuration and is exposed through Settings rather than being fixed in the React component. Side view ids, the Files side view target, the default side view, toggle behavior, and sidebar titles live in `workbenchSideViewModel.ts`; Activity Bar toggled context values, command registration targets, and Sidebar render branches consume those ids instead of duplicating side view strings. Sidebar command button handlers live in a focused Sidebar command model so open/refresh workspace command ids do not sit in the React shell. This keeps activity-bar command behavior, workspace-open follow-up, resource-opening follow-up, and sidebar labels aligned with focused sources of truth.

Export is a provider-backed platform service. `IExportService` owns provider registration, duplicate-format rejection, save routing, and provider context such as resource resolution and asset mode. The Markdown package contributes the current HTML provider using `marked`, while the Electron main process owns the save dialog and bounded file writes. When export providers need note resources, `IExportService` injects a resolver backed by `IResourceService` into provider input. When native saving is available, providers receive file asset mode; browser fallback uses inline mode so a single downloaded document remains usable. Extension runtime export providers register through `ExtensionContext.exports` and share the same provider lifecycle and cleanup path as other runtime contributions. The HTML provider uses a safe renderer that escapes raw HTML, drops unsafe link/image targets, pre-collects safe relative Markdown image tokens, and either rewrites resolved workspace images to sibling export assets or embeds them as data URLs. Missing or unavailable resources fall back to the existing safe relative image path instead of blocking export. Native export asset writes are bounded by shell configuration, reject invalid paths, reject non-image MIME types, and keep all asset paths inside the chosen export directory. Native saving only supports formats present in the desktop export configuration, so new runtime formats need matching shell support before they can use the native save dialog. Workbench registers an `Export HTML` command and toolbar action but does not render Markdown, resolve image paths, or write exported files directly.

AI integration is also provider-backed. `IAiService` owns provider registration, provider metadata, provider lifecycle change events, request normalization, and result normalization for text-generation style requests. Workbench bootstraps the service into `ServiceCollection`, exposes it through `ExtensionContext.ai`, subscribes to provider lifecycle changes through the centralized state subscription helper, exposes provider availability through the `ai.providerAvailable` context key, selects a default provider from metadata using stable title/id ordering, builds active-note AI requests through a focused request model, and provides centralized active-note writing action runners that compose provider selection, active model lookup, request construction, workspace search context selection, and `IAiService.requestText()` without UI-owned provider policy. Workbench registers summarize, rewrite, continue, and task-extraction commands only when a provider is available, contributes the summary command to the titlebar only when `ai.providerAvailable` is true, executes every writing command through the shared action runner, and renders provider responses in a bounded dialog with explicit copy plus action-specific application instead of mutating the note implicitly. A focused AI response model maps each action to its user-visible title and apply mode: summary, continuation, and extracted tasks append Markdown blocks, while rewrite replaces the active note through the text-file model. The response copy path uses a Workbench-local clipboard helper with injected browser environment adapters, keeping DOM permission fallbacks separate from AI provider logic. Response application uses a focused Workbench AI action helper that either formats provider output as an appended Markdown block or normalizes replacement Markdown before updating the active model through `ITextFileService.updateContent()`, keeping note mutation explicit and inside the existing text-file boundary. No built-in provider is registered by default. Platform configuration can now carry zero-default AI provider definitions for the Responses adapter: provider id, title, endpoint URL, model, secret reference, optional store preference, workspace context result limit, and workspace context preview limit as user-supplied configuration values. Settings edits those provider definitions and context limits through platform-owned normalization and writes only non-secret configuration values; saved-provider connection diagnostics go through a focused Workbench helper and `IAiService.requestText()` rather than calling the native bridge directly; API key save/delete actions go through a Workbench secret action helper and the Electron native AI bridge. In Electron, the provider factory uses that native bridge so Workbench passes only request body plus `secretRef`; the main process stores secrets through a shared `safeStorage`-backed native secret helper, decrypts them only for request execution, applies request/response byte limits and request timeout, owns the Authorization header, and accepts generated request ids plus cancel IPC messages so renderer `AbortSignal` cancellation can abort the main-process fetch. This keeps provider identity, model names, endpoints, and credentials out of Workbench UI and out of defaults. The platform contract carries instructions, user input, optional context items, metadata, cancellation signals, and token-usage metadata without naming a specific remote API, model, or secret-storage mechanism. Active-note AI commands build provider-neutral `workspace-search` context from `IIndexService` only when the workspace index is ready, exclude the active note, bound result count and preview length through configuration, and send snippets as context items rather than giving providers direct index access. Extension-host protocol messages broker AI provider registration, provider callback requests, and AI text cancellation across a future out-of-process host by forwarding service `AbortSignal` cancellation as a provider-scoped protocol cancel message. Future OpenAI Responses API, Codex SDK, local-model, or richer workspace-grounded providers should sit behind this boundary; Workbench surfaces should request AI work through commands and services instead of calling model SDKs or storing credentials directly. The practical first AI feature set is Markdown writing assistance: summarize, rewrite, continue, translate, extract tasks, and workspace-grounded Q&A using `IIndexService` for context selection. Codex is feasible for coding-agent and repository automation workflows, but it should not be the default writing assistant path because its product surface is optimized for software development tasks rather than ordinary note editing.

Remote synchronization follows the same provider-backed pattern. `IRemoteSyncService` owns provider registration, provider metadata, provider lifecycle change events, workspace resource/request normalization, sync plan creation, plan execution delegation, operation summaries, progress callback normalization, and conflict operation reporting. Workbench bootstraps the service into `ServiceCollection`, exposes it through `ExtensionContext.remoteSync`, subscribes to provider lifecycle changes through the centralized state subscription helper, exposes provider availability through the `remoteSync.providerAvailable` context key, and selects a default provider from metadata using stable title/id ordering, but no built-in provider is registered by default. Platform configuration can carry zero-default remote sync provider profiles for future native-request-backed adapters: provider id, title, base URL, optional remote scope id, bounded non-secret metadata, and named `secretRef` values; this gives future Feishu or other cloud setup surfaces a validated place for user-supplied connection metadata without storing decrypted tokens or built-in provider defaults. The platform remote sync model also converts trusted workspace file trees into normalized sync resources, optionally including directories, so Workbench surfaces and future providers do not duplicate path cleanup, root exclusion, or file metadata mapping. When the native workspace resource bridge is available, Workbench discovers Markdown-linked local images and attachments, verifies them through bounded workspace reads, and enriches file resources with bounded `sha256:` content hashes before provider planning; bridge-unavailable environments keep the previous size/mtime metadata path. Provider-returned plans, execution results, and execution progress events are normalized at the platform boundary, and plan/result summaries must match the actual operation counts before Workbench or extension brokers consume them. A focused Workbench remote sync request model builds dry-run workspace plan requests with provider-neutral metadata, while focused action runners select the default provider, call `IRemoteSyncService.createPlan()`, convert eligible plans into non-dry-run execution requests, and call `IRemoteSyncService.executePlan()` only after explicit user action. Workbench registers the `remoteSync.planWorkspace` command only when a provider and workspace are available, contributes the same command to the titlebar only when `workspace.open && remoteSync.providerAvailable` is true, then renders the returned plan summary and bounded operation preview in a dialog. A focused remote sync dialog model owns execute/cancel button state, blocked-state text, summary formatting, progress formatting, bounded progress history, conflict-focused bounded previews, bounded operation previews, and operation detail text. The dialog disables execution for conflict plans or no-op plans, shows why execution is blocked, highlights conflict operations from the same normalized plan data, displays running/cancel state plus the latest normalized provider progress while execution is pending, retains a bounded progress history for the current execution, passes an `AbortSignal` and progress callback into the execution request, aborts pending execution when Cancel or Close is pressed, and displays the normalized execution summary plus provider-returned execution operations after a provider runs. A shared diff planner compares local resources with provider-supplied remote snapshots, emits stable path-sorted create/update/skip/delete/conflict operations, classifies each operation's target side as local, remote, both, or none, defaults missing resources to non-destructive skips unless deletion is explicitly enabled, and treats uncertain bidirectional changes as conflicts rather than overwrites. A manifest-backed planner adds provider-neutral last-sync resources for bidirectional mirroring: if only one side changed since the synced baseline it produces a directed update, if either side deleted an unchanged baseline it still skips unless deletion is explicitly enabled, and if both sides changed, the baseline is missing, or state comparison is unknown it reports a conflict. `RemoteSyncManifestStore` adds a versioned manifest persistence boundary with injected storage, browser storage fallback, scoped storage keys derived from workspace URI, provider id, and remote scope id, strict write-time resource normalization, malformed snapshot rejection, and oversized/write-failure fallback to an empty manifest. Desktop builds resolve that manifest storage boundary through a narrow Electron preload bridge into main-process app data files; the main process validates storage keys, enforces configured value-size limits, and keeps Workbench/provider code away from filesystem paths. Remote sync secrets use a separate Electron preload bridge that exposes only provider-neutral set/delete operations; secret values are encrypted in app data through the shared native secret helper, while renderer and Workbench code work with `secretRef` values instead of raw tokens after handoff. A separate native request bridge lets future providers pass URL, method, non-sensitive headers, UTF-8/base64 body data, response mode, and `secretRef` bindings to Electron; the main process validates HTTPS or loopback HTTP URLs, blocks sensitive plain headers, injects secrets only into headers or top-level JSON fields inside the main process, enforces configured request/response/header/secret-binding limits, owns timeout/cancel handling, and returns bounded JSON, text, or base64 responses. A platform profile request helper combines validated profile base URLs, strict relative paths, structured query values, and named profile secret bindings into native request inputs, so future Feishu adapters can build endpoint calls without leaking route, token, or header policy into Workbench. A configured-provider factory layer then hands each profile and profile-scoped request transport to an injected adapter factory, and a Workbench synchronization helper mirrors configuration changes into `IRemoteSyncService` registrations while skipping existing provider ids; with no adapter factory available, no provider is registered. A raw mirror provider helper owns remote snapshot planning, manifest-scoped last-sync reads, delegated executable operation dispatch, and manifest refresh from adapter-returned post-execution remote snapshots; it rejects dry-run execution requests and conflict plans before adapter calls, preserves skip-only plans as no-op results, validates that planned executable operations match the current local/remote resource snapshots, validates that adapter-returned operations match the planned executable operation set exactly, and leaves cloud-specific list/upload/download/delete behavior in the injected adapter. `createRemoteSyncManifestResourcesFromExecution()` updates that last-sync baseline after provider execution only for create/update operations whose post-execution local and remote snapshots are both present, kind-compatible, and provably synchronized; delete operations remove baselines, while skip and conflict operations preserve the previous manifest. The platform normalizes provider-supplied operation targets so Workbench and future execution adapters do not infer mutation direction from `localUri` or `remoteId`. The platform contract carries workspace-relative resource metadata, direction, optional remote scope ids, metadata, dry-run intent, normalized progress messages, local cancellation signals, and optional operation-level progress without naming Feishu, OAuth, upload endpoints, or credential storage. Extension-host protocol messages broker remote sync provider registration and create-plan/execute-plan callback requests across a future out-of-process host; URI values become strings on the wire, service-side `AbortSignal` cancellation is forwarded as provider-scoped create/execute cancel messages that abort the runtime provider and suppress late results, and execution progress notifications are routed back to the originating broker request before final results arrive. Future Feishu Drive, raw file mirror, document-publish, or other cloud providers should implement this boundary, while Electron remains responsible for trusted local file access and future secret/network bridges. The practical first Feishu path is a raw Markdown/assets file mirror backed by a provider-supplied remote snapshot, a provider-neutral sync manifest, and upload/download execution adapters because it maps local file identity, content hash, timestamps, progress reporting, and conflict reporting directly into the existing sync contract. Publishing Markdown into Feishu Docs is possible as a later one-way export/import feature, but full Feishu Docs bidirectional sync is higher risk because Markdown text must be converted to and from Feishu's structured document block model while preserving unsupported Markdown syntax, asset references, comments, permissions, and remote edit conflicts.

Markdown renderer extensibility is also provider-backed. `IMarkdownRendererService` keeps renderer metadata separate from executable providers, mirroring the command metadata/handler split and the export provider boundary. Manifest contributions describe renderer id, label, block/inline kind, optional language, and priority; runtime providers register through `ExtensionContext.markdown` after activation. When `render()` is called for a known renderer without a provider, the service invokes its activation handler and retries provider lookup before failing. Unknown renderers do not trigger activation. `getRenderers()` reports whether a provider is available without exposing provider functions to Workbench callers. The platform service never inserts provider output into the DOM. Workbench adapts registered block renderers with matching code-fence languages into the editor through a `MarkdownCodeFenceRenderer` callback; the editor owns the capability gate, async preview widget lifecycle, source navigation, and HTML sanitization before provider output reaches the live-preview surface. Workbench also adapts registered inline renderers through a separate `MarkdownInlineRenderer` callback. Inline renderer previews are opt-in through language-qualified inline code spans such as `` `status:done` ``; ordinary inline code is left untouched. The editor sanitizes inline renderer output with a smaller inline-only allowlist before insertion, while still preserving source-focused click editing. The Workbench adapter keeps bounded LRU caches keyed by renderer id, active document URI, renderer language, and source content so viewport remounts reuse successful heavy render results; block cache keys also include code-fence info. The cache entry limit comes from editor configuration and `0` disables caching for diagnostics. Markdown configuration changes recreate the renderer adapters, naturally dropping cache entries that depended on old renderer preferences. Failed render attempts are removed from the cache so transient provider failures can recover. The built-in Mermaid provider lazy-loads Mermaid only when a `mermaid` code fence is previewed, renders SVG through Mermaid's engine with strict security settings, wraps the SVG as an encoded `data:image/svg+xml` image, and relies on the editor sanitizer to accept only safe encoded data-image sources and `tp-renderer-*` classes. The built-in Status provider renders `status` inline spans into compact escaped badges with existing theme tokens and reads its sanitized badge vocabulary from configuration at render time, keeping note workflow markers useful without adding editor-specific parsing logic beyond the generic inline renderer syntax.

## Remote Sync Adapter Notes

Configured remote sync provider factories may receive three bounded inputs: the normalized provider profile, a profile-scoped native request transport, and an optional trusted workspace resource bridge. Future cloud adapters should use those inputs instead of reading global state, constructing absolute filesystem paths, or storing decrypted credentials in renderer code.

The built-in configured raw mirror factory is metadata-gated with `rawMirror.adapter=raw-mirror`. It creates a native-request-backed raw file mirror only when a profile supplies relative list/upload/download/delete paths plus manifest storage and a workspace resource bridge. Secret material still lives in the profile `secrets` collection and native secret store: metadata only names a header binding, header name, and optional header scheme. The factory speaks a provider-neutral, file-only HTTP gateway contract, rejects non-2xx gateway responses before parsing payloads, ignores remote directory entries, and does not know Feishu hosts, OAuth scopes, tenant tokens, folder ids, or provider-specific rate-limit semantics.

Settings pre-validates configured raw mirror metadata before saving a remote sync profile. The validation reuses the platform-owned raw mirror metadata keys, requires relative list/upload/download/delete gateway paths, and requires optional header binding metadata to point at an existing profile secret. This keeps Settings from persisting profiles that the configured factory would skip or that would later run without the intended native secret injection.

Configured raw mirror gateways can opt into bounded retry by metadata, listing retryable HTTP status codes plus optional retry count and delay values. The execution path retries before response parsing and still fails with the final non-2xx gateway status when retries are exhausted. `Retry-After` is honored as a standard HTTP delay hint, while provider-specific token refresh, rate-limit body parsing, multipart sessions, and folder mapping remain adapter responsibilities.

Raw mirror upload staging is provider-neutral. `readRemoteSyncRawMirrorUploadFileContents()` reads only local file resources for executable create/update operations targeting the remote side, refreshes size/mtime/content hash metadata from `IRemoteSyncWorkspaceResourceService`, reports per-resource progress, and rejects missing, duplicate, aborted, or mismatched reads before provider-specific upload code runs. Directory creation, remote upload endpoints, remote folder ids, provider-specific retry body parsing, and provider-specific response parsing remain adapter responsibilities.

Raw mirror local application is also provider-neutral. `applyRemoteSyncRawMirrorLocalResourceChanges()` writes downloaded base64 file content for executable create/update operations targeting the local side, deletes local resources for delete operations, carries expected mtime into trusted workspace writes/deletes, avoids create-over-existing and update/delete-without-local-resource cases, and validates downloaded file paths plus base64 payloads before native writes. Provider adapters still own remote download requests, remote folder semantics, and translating remote API responses into workspace-relative downloaded file contents.

Manifest refresh uses post-execution snapshots when an adapter can provide them. `createRemoteSyncRawMirrorExecutedLocalResources()` merges refreshed upload reads, local apply results, and existing local resources into a sorted local resource snapshot, and `createRemoteSyncRawMirrorProvider()` prefers adapter-returned local resources over the pre-execution request resources when writing the last-sync manifest. This lets future pull/download adapters record the local state that actually landed on disk without moving provider-specific remote I/O into the platform layer.
